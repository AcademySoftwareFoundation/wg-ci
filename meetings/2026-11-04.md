* Major aswfdocker and GHA revamp
  * aswfdocker is the Python component which drives the build of the aswf-docker CI images
    * Main goals:
      * Automate release process (currently can take up to 2 days of sequential steps and careful monitoring of GHA)
      * No longer need to track dependencies manually (let Conan do its thing)
      * Security improvements: SBOM, GHA hardening
  * Leverage Conan dependency tracking instead of hand maintaining "layers of packages" which have to be built in a specific order
    * We still want to build each package in its own container instance for full isolation:
    * aswfdocker first calls Conan to produce a build order report which it then uses to fire off individual package builds instead of telling Conan to "build everything"
    * Qt still takes enough time to build that it has its own explicit build step
    * CLI options to resume a build from a specific package during a release cycle so you don't have to rebuild from scratch
    * Each container build fired off as separate GHA job, can run in parallel. For local builds still have to build sequentially due to Conan build cache sqlite dependency
      * Will use separate caches for separate VFX years to allow cross-year build parallelism
  * Starting on BOM generation
    * Each Conan package stores git SHA in package metadata uploaded to Artifactory
    * No more "spurious" GitHub release tags for Conan packages, only ci-images uploaded to Docker Hub
    * Conan leveraged to create SBOM (CycloneDX format for now) stored in container image, including git sha from which package was built
      * Andy: I recommend going with CycloneDX format, the SPDX format doesn't have the industry support for CycloneDX. Our tooling is using CycloneDX, and there are lots of tools that don't read SPDX.
      * Stephen: you can use CycloneDX to generate SPDX. May not be in the Conan version since they have an older version, their support was experimental.
      * Andy: some incompatibility between formats, majority of tooling will know CycloneDX.
      * Stephen: if you need to do something to the Conan CycloneDX process, you can hook into the internals. It's flexible, I recommend it. At NVIDIA we have our own versions of upstream formats, the upstream CCI versions are what the CVE is reported against, if you built it yourself with your own patches, it's a new hash. No way to tell the SBOM that you've patched the CVE yourself. A naive CVE detector may think you have CVEs.
    * SBOM attached to GitHub release tag for ci-images
    * Does not yet address non-Conan components: base Rocky Linux distribution, NVIDIA components...
  * Restructure GHA to support new release mechanism
    * Better handling of secrets (Artifactory / Docker Hub keys)
    * Zizmor scanning as a pre-commit hook and GHA job
    * Andrew: spec driven development. Try to have the initial spec to cover the majority of what I need, have it broken down in phases during planning stage. But trying to add features to an existing system, features should be fairly targeted. Won't ever get to a perfect "waterfall". At first would take a day or 2 to work with agent to create the spec, these days I know better the initial prompt so the turnaround for a clean spec is more like a day. I look over the spec it produces, and work with the agent on the plan. The analysis might find some gaps, but in general I can have the agents start doing implementation the same day I start working on it. Usually can tell the agent to work on agent to work on all phases unless it requires interaction. In some cases will have lots of interactions along the way.
    * JF: I did it in steps so I could review code and update requirements. Andrew: started that way, but experience means you will have less of that to do. Agent will mostly do the right thing. As you get more familiar, the less that happens.

* Zizmor
  * GHA linting, simple to add, big payoff
  * In a uv based project, add it to your pyproject.toml
  * In your .pre-commit-config.yaml:
    * entry: uv run zizmor .github/workflows
  * Will go through every ASWF project and open issues for those that don't have it (or some kind of GHA scanning) yet
  * Andrew: we also recommend "aislop", it will do a lot of code smell checking to put guardrails around agentic code. Also gripescanning. For GitHub Actions I would recommend Actions Lint, primary repo has gone dormant, but there's a [fork LF RelEng is using](https://github.com/kjanat/actionlint). Look at the [pre commit hook in this repo](https://github.com/lfreleng-actions) as well as LLM documentation. We rolled out fixes in less than a week for the CVEs from the big bad week, a slew of issues around GHA as well.
  * Andrew: if you see kernel updates for your distro, pick them up right away.

* Phantom PRs in GitHub
  * Observed by Cary on OpenEXR
  * If account submitting a PR gets banned, PR can disappear even if it was merged into project
  * And then it comes back...
  * Stephen: ran into a similar issue, had an issue on a non-ASWF project, someone posted a PR on the issue, was commenting on it, and it was suddenly gone from GitHUb and the issue. I had an agent working on the PR, it remembered the name of the user, and that user was gone. No evidence that the user existed. So started my own PR, got distracted, and a couple of weeks later the PR and user was back again. This was on a repo that gets a lot of AI-generated PRs, so lots of users are bots. GitHub shadowbanned that user because of too much volume / activity, the user appealed it, and it was unbanned. That is still weird, how do I trace this back to where it came from.
  * Andrew: they've been doing this forever, but now it happens more often. Stephen: also destroys the traceability. Jon: seems there should be a better way... Andrew: the metadata only disappears from open changes, not after they were merged in. The commit itself will live on, but not the PR it came from.

* CMake project NAMESPACE for targets
  * Not every project uses the NAMESPACE option when calling install()
  * Results in un-namedspaced CMake symbols, for instance `MaterialXCore` instead of `MaterialX::MaterialXCore`
  * Can be worked around by adding aliases
  * Should ASWF projects be suggested (required?) to adopt namespacing for CMake targets?
  * Considered [best practice for Modern CMake](https://www.kitware.com/psa-your-package-name-and-target-namespace-should-match/)
  * More generally, would a "Cmake Symposium" to seek CMake unification and best practices across ASWF projects make sense? And/or point an LLM at every ASWF project and ask for a critique (similar to "Project Health Check")
